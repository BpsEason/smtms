# SMTMS AI Agent 任務執行模板

## 標準任務執行流程

### 步驟1：需求範圍確認
- 明確任務需求的輸入、輸出、預期行為
- 識別涉及的核心模組與業務流程
- 確認是否需要修改資料庫結構
- 確認是否涉及權限變更
- 列出需要查證的關鍵資訊

### 步驟2：相關程式碼調查
- 沿依賴鏈調查相關的路由、模型、服務
- 確認現有實作模式與命名慣例
- 檢查相關業務規則（DR-XXX）的實作狀態
- 驗證資料關聯與約束
- 查找同類功能的實作範例

### 步驟3：根因或實作方案分析
- 若為Bug修復：確認根因、影響範圍
- 若為新功能：評估最小修改方案
- 確認是否需要新增資料庫欄位
- 確認是否需要新增API端點
- 評估回歸風險

### 步驟4：修改檔案確認
- 列出所有需要修改的檔案
- 確認每個檔案的修改範圍
- 確認是否需要同時修改前後端
- 確認是否需要更新遷移文件
- 確認是否需要新增測試

### 步驟5：實作
- 遵循既有程式設計慣例
- 維持最小修改原則
- 確保供應商資料隔離
- 維持追溯鏈完整性
- 加入適當的錯誤處理

### 步驟6：相關測試
- 執行相關的單元測試
- 執行相關的整合測試
- 手動驗證核心流程
- 檢查程式碼風格與型別正確性
- 確認沒有引入新的警告

### 步驟7：回歸風險確認
- 評估修改對其他模組的影響
- 確認沒有破壞既有功能
- 確認業務規則仍然被遵守
- 確認供應商隔離仍然有效
- 確認追溯鏈完整性

### 步驟8：完成報告
提交包含以下內容的完成報告：
- 修改：做了什麼修改
- 檔案：修改了哪些檔案
- 原因：為什麼這樣修改
- 驗證：做了哪些測試驗證
- 結果：驗證結果如何
- 風險：是否存在剩餘風險

## 特殊場景處理流程

### Bug修復任務
1. 重現問題
2. 定位根因
3. 評估影響範圍
4. 最小修正實作
5. 驗證修正有效
6. 檢查回歸問題

### 新功能開發任務
1. 確認需求細節
2. 檢查是否有現有類似功能
3. 規劃API/UI修改
4. 實作前後端
5. 寫入必要測試
6. 驗證功能完整

### 資料庫修改任務
1. 確認修改必要性
2. 檢查既有Schema約束
3. 建立正確的遷移文件
4. 確保資料一致性
5. 測試遷移的回滾
6. 更新相關文件

## 高頻任務標準調查順序

### 場景1：新增/修改涉及供應商資源的API
必須按照以下順序檢查檔案，確保符合供應商資料隔離規範：
1. **第一步：確認核心隔離機制**
   - 讀取`backend/app/core/security.py`中的`ensure_supplier_access`實現
   - 檢查當前使用者是否能正確取得`current_user.supplier_id`
   
2. **第二步：檢查既有同類API實作**
   - 查看`backend/app/api/routes/suppliers.py`中現有巢狀資源的實作範例
   - 確認是否在進入點呼叫`ensure_supplier_access`
   - 列表查詢是否在資料庫層加入`supplier_id`過濾條件

3. **第三步：驗證相關業務規則**
   - 查閱`.ai/business_rules.md`中涉及供應商的DR規則
   - 確認新修改符合DR-001（供應商代碼唯一性）、DR-011（使用者隔離性）等約束
   
4. **第四步：檢查模型關聯**
   - 讀取`backend/app/models/quality.py`中相關ORM模型
   - 確認資料表之間的外鍵關聯正確
   - 驗證新資源是否有正確的`supplier_id`欄位

5. **第五步：測試案例規劃**
   - 準備跨供應商存取的測試案例
   - 規劃內部使用者與供應商使用者的權限測試
   - 設計邊界條件的測試場景

### 場景2：修改品質流程（收料/拆分/IQC）
必須按照以下依賴鏈檢查順序，確保追溯鏈完整性：
1. **第一步：追溯鏈上游依賴確認**
   - 從底層向上檢查：供應商批次(supplier_lots) → 收料紀錄(material_receipts) → 內部批次(internal_lots) → IQC記錄(iqc_records)
   - 確認修改不會中斷任何環節的關聯
   
2. **第二步：檢查現有品質流程實作**
   - 讀取`backend/app/api/routes/quality.py`中的相關函數
   - 檢查`split_receipt_into_internal_lots`等核心函數的實作方式
   - 確認既有交易處理、鎖定機制是否需要沿用

3. **第三步：驗證相關業務規則**
   - 查閱`.ai/business_rules.md`中品質相關的DR規則
   - 特別注意DR-006（拆分數量限制）、DR-008（IQC結果與放行狀態配對）、DR-009（追溯鏈關聯一致性）
   
4. **第四步：交易與併發控制檢查**
   - 確認是否需要使用`with db.begin():`界定交易範圍
   - 評估是否需要類似access.py的advisory lock機制
   - 檢查是否有數量一致性的檢查邏輯

5. **第五步：狀態轉換驗證**
   - 確認修改符合DR-013（內部批次狀態流轉）
   - 驗證所有狀態轉換都是合法的
   - 測試邊界條件下的狀態變更

## 強制檢查清單
任何任務完成前必須確認：
- [ ] 遵守所有SKILL.md中的開發規範
- [ ] 維持供應商資料隔離
- [ ] 不破壞追溯鏈完整性
- [ ] 前後端API契約一致
- [ ] 程式碼風格符合既有慣例
- [ ] 相關測試通過
- [ ] 沒有引入安全漏洞
- [ ] 文件有適當更新
